## The goal

Anyone should be able to rebuild EspOS for their own hardware by adding **one folder** that describes the board and holds its drivers, without touching the OS core, the runtimes or any package. The OS asks the board layer, never a specific board.

## The layout

<FileTree>
- src/
  - hal/
    - board.h `hal::Board` (the descriptor), `hal::Bsp`, `hal::detect()`
    - caps.h capability flags and their package-facing names, the profiles
    - display.h `hal::DisplayDesc` and the `hal::Display` driver interface
    - input.h `hal::InputDesc` and the `hal::Input` driver interface
    - audio.h, storage.h, power.h the codec, the card slot and the battery, as data
    - hal.cpp `hal::i2cAnswer` for probes
  - boards/
    - boards.cpp the registry
    - es3c35p/
      - es3c35p.h the descriptor
      - bsp.cpp `probe()` and the `hal::Bsp`
      - display.cpp
      - touch.cpp
    - es3c28p/ the same four files
    - qemu/ the boards as QEMU emulates them
    - _template/ a commented starting point for a new board
</FileTree>

### A board support package

```cpp
// src/hal/board.h
struct Bsp {
  const Board* board;      // the descriptor
  uint8_t (*probe)();      // is it this board? the I2C address that answered, 0: no
  const Display* display;  // the panel driver
  const Input* input;      // the touch driver (nullptr: none)
};
```

The descriptor is `constexpr` data in flash. Drivers read it at compile time, so a pin from the descriptor costs no more than a `#define`.

### The registry

`src/boards/boards.cpp` lists the boards one firmware supports, in the order they are probed at boot. The first `probe()` that answers wins; if none does, the first board in the list is used. Simulator, QEMU and single-board builds list one board and skip probing.

### Capabilities

Each descriptor lists what its board has as `CAP_*` flags from `src/hal/caps.h`. Each flag has exactly one package-facing name (`CAP_TOUCH` is `input.touch`), kept 1:1 by a compile-time check; the table is in [Capabilities](/hardware/profiles/#capabilities). The OS already gates its audio, card and battery drivers on them, and they define the [hardware profiles](/hardware/profiles/).

## Keeping the platform skeleton

A board package changes how the OS reaches the hardware, never what the OS offers. Every board keeps the same [contract with packages](/hardware/#what-a-port-must-keep): the EspOS API, the 320 × 480 logical screen in portrait and 480 × 320 in landscape (scaled on a smaller panel), memory for apps, the package format and storage, and the server protocol. That is what lets one store serve every board.
