Boards differ a lot: some have megabytes of PSRAM and a fast colour touch screen, others a small monochrome screen and a button. EspOS describes each device by its **capabilities** and its **runtimes**, and gives common sets of them a name: a **profile**. Packages never name a profile; they name capabilities.

| | Full |
|---|---|
| Status | <Status s="available" /> |
| Chip | ESP32-S3 |
| Memory | 8 MB PSRAM, 16 MB flash |
| Screen | colour LCD, fast; the interface in portrait or landscape (scaled on smaller panels) |
| Input | capacitive touch |
| Devices | the S3 desks: ES3C35P (3.5"), ES3C28P (2.8") |
| Runtimes | JavaScript (API level 1), the engines (`pet`, `run`, `j2me`), the language packs; declarative to build; WebAssembly later |

The **EspOS Bot** (an ESP32-S3 with PSRAM, a 0.96" OLED of 128 × 64, a microphone, a speaker and one button) runs its own firmware for the dog assistant. It shares the wake word and the licence code with the desks, but it has no app runtime and installs no packages from the store, so it has no profile yet.

## Capabilities

<Status s="planned" /> A package will say what it needs in a `requires` list, and a device will report what it has. A package fits a device when every flag it requires is in the device's list and the device has the package's runtime at the needed level. The store will offer only the packages that fit, and grey out the rest with the reason, such as "Needs a touch screen".

| Name | Firmware flag | Meaning | Full |
|---|---|---|---|
| `screen.color` | `CAP_COLOR` | 16-bit colour or better | yes |
| `screen.gray` | `CAP_GRAY` | 4 grey levels or more | yes |
| `screen.eink` | `CAP_EINK` | the picture stays without power; slow refresh | |
| `screen.fast` | `CAP_FAST` | 20 frames a second or more (animation, games) | yes |
| `input.touch` | `CAP_TOUCH` | a touch screen | yes |
| `input.buttons` | `CAP_BUTTONS` | at least Back, OK, Up and Down | |
| `mem.psram` | `CAP_PSRAM` | 2 MB or more of external RAM | yes |
| `audio.out` | `CAP_AUDIO_OUT` | a speaker | yes |
| `audio.in` | `CAP_AUDIO_IN` | a microphone | yes |
| `store.sd` | `CAP_SDCARD` | a memory card slot | yes |
| `net.wifi` | `CAP_WIFI` | WiFi | yes |
| `net.ble` | `CAP_BLE` | Bluetooth LE | yes |
| `power.battery` | `CAP_BATTERY` | a battery the firmware measures | yes |
| `led.rgb` | `CAP_RGB_LED` | an RGB LED | yes |

`screen.eink` and `input.buttons` are named now so that packages and boards agree on them before a device has them. The firmware also defines a **Lite** set (`hal::PROFILE_LITE`: no PSRAM, an e-ink panel, buttons) for such boards; no supported device uses it today.

The screen size is not a flag: a device reports it and whether it can turn. Packages name capabilities, never profiles, so a new board that sits between two profiles (an S3 with an e-ink panel, a board without PSRAM) works with existing packages on the day it ships.

In the firmware, each board's descriptor carries these as `CAP_*` flags (`src/hal/caps.h`). Every flag has exactly one name and every name one flag, checked when the firmware compiles; a new capability is a flag, its name and its line in this table, added together. See [Board-specific code](/hardware/board-code/#the-descriptor).

## Declarative packages

Faces, widgets and themes are **declarative**: a JSON file of boxes, text, icons and data bindings that the firmware draws itself. They cannot loop, allocate or use the network, so they need no code review and run on a device with no room for a script runtime. One file carries a layout per screen shape and scales to the others. The format is in [Declarative faces and widgets](/reference/decl/); the S3 desks do not draw it yet.

## Full <Status s="available" />

Everything else in these docs is the Full profile: JavaScript apps with a 1.5 MB heap in PSRAM, Java games, the run game at 20 frames a second, a touch interface laid out for portrait and landscape. A board in this profile needs an ESP32-S3, 8 MB of PSRAM, 16 MB of flash, a colour panel and capacitive touch; see [Port to a new board](/hardware/porting/#before-you-start).

<Aside type="note">
A board can have more than its profile requires, or lack an optional part such as a speaker or a card slot. Packages must cope when a part is missing; on a board without a speaker, for example, `sound.*` calls play nothing.
</Aside>
