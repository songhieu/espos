An app can go to two places.

| Where | Who can put it there | How |
|---|---|---|
| **Your own devices** | You, today | Upload it to your espos.dev account with `espos upload` or the web's **My apps** tab. Only your devices install it. See [Put your app on your own device](/guides/my-apps/). |
| **The public store** | The store's owner, today | The owner publishes the catalog with a temporary key (below). Submissions from everyone, with a review queue, are <Status s="planned" />. |

<Aside type="note" title="Try it on your own devices first">
You do not need the store to run your app on real hardware: a private upload installs it on every EspOS S3 of your account over WiFi, and a higher `code` updates it. Put it in the store when other people should get it.
</Aside>

<Aside type="caution" title="The public store is curated">
Only the store's owner publishes to the official catalog, with a temporary upload key that is revoked right after each upload. If you have an app for the store, prepare it as described below and contact the EspOS project. Your private uploads never reach the store.
</Aside>

## Before you submit

- [ ] The `id` is final. It can never change after the first release.
- [ ] `code` is higher than the last published one. Devices compare codes, not versions: a new build with the same `code` never reaches anyone who has the package.
- [ ] `name` (at most 40 characters), `desc` (one line, at most 300) and `author` (at most 40) are short and plain, with no ellipsis.
- [ ] `perms` lists only what the app uses.
- [ ] The icon is a square **baseline** JPEG, 120 × 120, under 200 KB, or a gradient and glyph in the manifest.
- [ ] Every screen was opened in the [simulator](/guides/simulator/), and the app was run in [QEMU](/guides/qemu/) or on a board.
- [ ] Screenshots for the store are baseline JPEGs of the 320 × 480 screen.
- [ ] The app was opened in landscape too (`rot 1` in the simulator), and in another language if it has translations.
- [ ] For a Java game: its licence allows redistribution, and the description says which.
- [ ] `tools/espk.py --check` (or `espos check --strict`) passes.

## How a package is published

<Steps>

1. **Dry run.** The publish script reads every `.espk`, checks its header, manifest, file table and every CRC32, checks that the parts of one package share `id`, `version` and `code` with exactly one `core`, and prints the upload plan and the merged catalog. Nothing is uploaded.

   ```sh
   python3 scripts/publish_pkg.py --dry-run out/com.example.teatimer-1.0.0-core.espk
   ```

2. **Upload.** With a temporary key in the environment, the script uploads each part as `apps-s3/<id>-<version>-<part>.espk`, the icon as `<id>-<version>.jpg`, screenshots as `<id>-<version>-shot<n>.jpg`, and **the catalog last**, so the catalog never points at a missing file.

   ```sh
   ESPOS_BBK=<temporary key> python3 scripts/publish_pkg.py out/com.example.teatimer-1.0.0-core.espk --shot shot1.jpg
   ```

3. **Merge.** The script merges one entry per package id into `apps-s3/catalog.json` and keeps everything else.

4. **Devices see it** the next time they load the catalog: when the store opens, and at least every 6 hours while automatic updates are on. When the new `code` is higher than the installed one, an installed copy updates by itself while it is not in use. Users who turned automatic updates off get "Update" in the store instead. See [Updates](/concepts/store/#updates).

</Steps>

| Option | Meaning |
|---|---|
| `--dry-run` | Check and print the plan and merged catalog; upload nothing. No key needed. |
| `--catalog FILE` | Merge into a local `catalog.json` instead of the live one (an offline check). |
| `--out FILE` | Also write the merged catalog to a file. |
| `--replace` | Allow publishing the same version again with different bytes. Devices that have it keep theirs. |
| `--shot FILE.jpg` | A screenshot for the store. Repeat for more. |
| `--meta FILE.json` | Part choices (group, label, default) from a build tool's catalog entry. |

The `espos` CLI wraps the same script: `espos store publish dist/*.espk` is a dry run, and `--yes` uploads. <Status s="preview" />

<Aside type="note" title="The key never touches the command line">
The upload key is read only from the `ESPOS_BBK` environment variable, by the publish script itself. It is never printed, passed as an argument or stored.
</Aside>

## Parts in the catalog

The core part and every part without a `group` are required. A part with a `group` is a choice: an install takes exactly one per group, its `default` unless the user picks another, and the store shows its `label`. The script takes these from, in order: the part's own manifest, a build tool's catalog entry next to the files (`<id>-<version>-catalog.json`), and the core manifest's `parts` list, which wins. See [Store catalog](/reference/catalog/).

## Submit to the public store<Status s="planned" />

This is the design; none of it is live yet. Publishing the official catalog stays as it is above: a submission only ever reaches the catalog through the owner's approval and the same publish step.

<Steps>

1. **Upload privately first.** The app is an upload in your account, tested on your own devices (`espos upload`).

2. **Submit it.** `espos submit u.vn.you.teatimer` (or **Submit to the store** next to the app in **My apps**) asks for review. The store id is the manifest's id without `u.`. An id belongs to the first account that publishes it; a taken id is refused at once.

3. **Automatic checks.** The server runs the validator again, then the app in a headless simulator: it opens every screen the smoke script reaches, saves screenshots for the store page and fails on an exception.

4. **Review.** The submission waits in a queue on the admin page. The store's owner (or an admin) reads the manifest, the permissions, the licence and the screenshots, and approves or rejects it with a reason you see in **My apps** and `espos apps`.

5. **Publish.** An approved package goes through the owner's publish step above (`publish_pkg.py`): its file is copied to `apps-s3/`, the catalog is written last. Devices see it at their next catalog load.

6. **Updates.** A higher `code` from the same account goes back into the queue. One that asks for no new permission is reviewed first.

</Steps>

Your private copy (`u.vn.you.teatimer`) keeps working next to the store version; they are two apps on the device, each with its own saved data.

## Also planned<Status s="planned" />

- **A developer page** on the web with your submissions, their review state and download counts.
- **Human review** for `net`, `bg` and new authors.
- **Signed packages and catalogs:** Ed25519 developer keys (updates need the same key) and store-signed catalogs with an expiry.
- **Several catalog sources:** a self-hosted server can mirror the official store, and devices can add other catalogs.

Store content belongs to its authors and stays exportable.
